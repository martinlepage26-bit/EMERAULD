## Summary

`AGENT_PROTOCOL_FOR_WORKING_WITH_MARTIN.md` is a 24-section operating protocol for any agent collaborating with Martin Lepage across scholarship, software, clinical research, AI governance, writing, design, and public intellectual work. Its governing rule: an agent should preserve the architecture of the work while moving it toward release — not smooth difficulty into generic helpfulness. Core mandates: protect voice and authorial pressure, test claims rather than agree by default, enforce stated constraints as the task itself, distinguish direct evidence from inference from speculation, and track every project's status, next action, unresolved risk, and definition of done.

## Details

The 24 sections group into five functional clusters (verified facts — this is a direct paraphrase of the source structure, not inference):

1. **Posture and claim discipline** (§§1–5, 14) — treat every substantial request as part of a larger architecture (governing claim, object, constraints, evidence, risk, next step); default to pressure-testing ideas rather than agreeing; convert conceptual pressure into a governed claim (claim → mechanism → evidence → scope → consequence → risk); structure paragraphs as claim → mechanism → implication.
2. **Voice and evidence protection** (§§2, 6, 12) — do not over-polish Martin's writing into anonymous academic fluency; preserve the sentence that turns, the claim that cuts, controlled heat over smoothness; label the evidentiary function of every source (definition, finding, method, critique, etc.) and never launder uncertainty into authority; handle personal/biographical material (Saguenay origin, recovery, fieldwork) as structure, never decoration.
3. **Recursive work style and project state** (§§7, 13) — Martin typically starts from fragments, not finished briefs; the agent should infer architecture from messy input without erasing the mess too early, and track whether each project belongs in a live queue, archive, graveyard, submission track, or deployment track. "A project without a release path risks becoming an intellectual landfill with better filenames."
4. **Domain-specific protocols** (§§8–10, 17–18) — scholarly writing should be publication-oriented by default; French/English translation must preserve density and rhythm rather than flattening into neutral international English (Quebec register preferred over European register when writing in French); software/AI projects are governance objects (what decision becomes reviewable, what burden moves, what failure becomes visible); technical and visual/asset requests require exact executable specifics (commands, file paths, pixel dimensions, file-size verification), not abstract advice.
5. **Constraint enforcement and self-check** (§§11, 19–24) — stated constraints (file limits, formats, deployment environments, word counts) are the task itself, not a preference to approximate; the source lists explicit anti-patterns to avoid (generic encouragement, flattening voice, ignoring constraints, decorative citations, sentimentalizing personal material, claims stronger than evidence) and a compact pre-answer checklist (§23); the file closes with a one-sentence operating rule (§21) and a minimal invocation prompt (§22) suitable for cold-starting a new agent session with this posture.

**One-sentence operating rule (§21, quoted verbatim):** "Before responding, identify the governing object, protect the authorial pressure, enforce the constraints, test the claim, and move the work one step closer to release."

Inference (not stated in the source): this protocol reads as the personal/interpersonal analogue to the three-agent governance model (Hephaistos/Queen Keyport/Hermes) already documented in the vault — the three-agent model governs how *automated agents* divide labor and authority; this protocol governs how *any single agent* should relate to Martin as a collaborator regardless of which tier it occupies.
