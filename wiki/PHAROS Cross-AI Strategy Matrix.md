# PHAROS Cross-AI Strategy Matrix

## Summary

The role-and-function matrix for the deliberate cross-AI workflow in the [[PHAROS Method — Technical Reference|PHAROS]] project. Documents how different AI systems were used against and through one another — not as a sequence of replacements, but as a distributed prompt-forging, claim-pressure, and implementation strategy. See [[AI Personas — Agatha, DOTTIE, and MOBI]] for the personas that anchor this matrix.

## Context

This file is the companion to [[PHAROS AI Lineage — Source of Truth]]. Where the lineage document provides chronology, this matrix isolates the governing claim: the project treated cross-use of AIs as a method — a way to resist single-model closure and force triangulation. It is referenced directly by the [[AI Paper Prompt — PHAROS Recursive Workflow Case Study]] as the role-and-function aid for reconstructing the cross-AI workflow. The forge and implementation surface (Claude / Codex) maps directly onto the current [[MASTERxMASTERxMASTER — Skill Corpus Map|skill corpus]] and [[PHAROS Recalibration — Unified Governance Architecture|governance architecture]].

## Details

**Governing claim:** The project did not accumulate AI tools over time. It deliberately used different AIs against and through one another to generate prompts, pressure claims, test phrasing, and distribute functions across a recursive workflow.

**Role matrix by system:**

| System | Primary Role | Platform | Evidence |
|---|---|---|---|
| **Agatha** | Relational interface; authorship-support partner | ChatGPT Plus | Supported |
| **Voice Operator 1** | Containment; admissibility; workflow discipline | Governed GPT | Direct |
| **Henry** | Manuscript builder; reviewer-facing operator | Governed GPT | Direct |
| **Dottie** | Claim audit; anti-inflation critique; prompt-pressure | ChatGPT Business | Direct (critique voice); Supported (prompt-pressure) |
| **Gemini Pro** | Prompt creation; diagnostic and repair prompting | Gemini Pro | Supported |
| **Claude** | Forge layer; cross-agent implementation; prompt creation | Claude / Hephaistos WSL | Direct |
| **Mobius** | Self-polygraph; truth discipline; recursive self-test | ChatGPT Business + desktop | Direct |
| **Codex** | Operational implementation; downstream build surface | Codex via WSL / Hephaistos | Direct |

**Mechanism summary:**
1. One AI helps generate or refine a prompt
2. Another pressures the claim or structure produced by that prompt
3. Another becomes the forge or implementation surface
4. Disagreements expose blind spots rather than being hidden as noise

The Mobius self-polygraph function connects to the [[Möbius Protocol — AI Self-Polygraph Template]] and the broader [[Self-Polygraph Protocol and Suprametacognition]] practice. Dottie's claim-audit role is documented in the [[PHAROS Evidentiary Gap Closure Bundle]].

2026-04-29 synthesis: [[Second Self System — Identity Kernel and Agent Routing Architecture]] is the operational answer to the matrix's sprawl problem. Cross-AI disagreement remains useful as method, but public output should pass through one identity kernel, one orchestrator, and one public voice.

**Boundaries:**
- The archive supports cross-use as strategy better than it supports a fully dated log of every prompt handoff
- Dottie is strongly present as critique logic; standalone GPT packet is thinner than Henry's
- Gemini Pro prompt creation is user-confirmed and archive-supported, but not fully reconstructed as a dense chronological packet

**Evidence labels used in source:**
- `Direct` — clearly evidenced in accessible artifacts
- `Supported` — backed by multiple traces plus user correction, but not always fully packeted as one clean spec
- `Thin` — plausible but still weakly evidenced in the currently opened packet

## Key Ideas

- Cross-use of AIs is a workflow strategy and claim-pressure mechanism, not random platform-hopping
- Separating relation, governance, critique, and implementation across systems prevents single-model closure
- Disagreement between systems is treated as method; triangulation is the goal
- Evidence labels (`Direct`, `Supported`, `Thin`) apply throughout — do not promote `Supported` to `Direct` without packet evidence
